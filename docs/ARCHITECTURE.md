# OpenBand DAW — Design notes

How OpenBand is put together and why. For installation and usage see the [README](../README.md). The project file format is described in [PROJECT_FORMAT.md](PROJECT_FORMAT.md).

## Goals

- **Lightweight.** Plain TypeScript and the Web Audio API, with no UI framework and no runtime dependencies. The production bundle is about 140 kB of JavaScript (under 50 kB gzipped).
- **Self-contained sound.** Every instrument, effect and impulse response is generated by code, so the repository holds no sample libraries or recorded audio.
- **One codebase, two targets.** The same build runs in a browser and inside an Electron shell for the desktop installers.
- **Predictable.** What you hear while playing is exactly what the offline WAV export renders.

## Module map

│   ├── fx/            effect definitions, effect modules, insert chain
│   ├── worklets/      drive (saturation) and recorder AudioWorkletProcessors
│   ├── ir.ts          procedural reverb and cabinet impulse responses

│   ├── pitch.ts       YIN pitch detection for the tuner

`core/` and the pure parts of `dsp/` and `synth/` have no DOM or audio dependencies, so they run under Node in the unit tests.

## Data model and state

- The **project** is a plain JSON-serialisable object, and it is the single source of truth. Positions and lengths are in **beats** (quarter notes), so changing the tempo never moves notes.
- `Store` holds the project and the UI state (selection, zoom, open tab…). It broadcasts a *change reason* so each view does the minimum work:
  - `structure` rebuilds DOM panels;
  - `params` only refreshes values and redraws canvases;
  - `selection`, `view` and `transport` don't touch the project.
- **Undo/redo** stores JSON snapshots of the project, without the audio pool. Recorded audio is append-only and can be large, so it stays out of the history.
- Continuous gestures (dragging a note, moving a slider) take **one checkpoint at the start** of the gesture, so a whole drag is a single undo step.

## Audio engine

`AudioEngine.sync(project)` reconciles the live node graph with the project after every change. It creates or disposes channel strips by track id, swaps instruments when the engine type changes, applies parameters incrementally and rewires effect chains only when their order or bypass state changes. Undo, loading a file and live editing all go through this same path.

### Signal flow

```
instrument / audio input ─▶ [insert 1] ─▶ … ─▶ fader ─▶ stereo up-mix ─▶ pan ─▶ mute/solo gate ─▶ master bus
master bus ─▶ [master inserts] ─▶ master volume ─▶ safety limiter ─▶ output
```

- **Stereo up-mix before the panner.** A `StereoPannerNode` attenuates mono input by 3 dB at centre but passes stereo input at unity, so the output of a stereo effect would jump in level. Every strip is up-mixed to stereo (at the mono level) before panning.
- **Safety limiter.** A fast, high-ratio compressor just below 0 dBFS. The master meter taps the signal *before* the limiter, so overs still show red.
- **First update is immediate.** New strips and effect modules jump straight to their settings; later changes glide over about 15 ms to avoid zipper noise. Without this, the first milliseconds of playback or export would pass at default levels.

## Timing

- **Clock.** A tiny Web Worker posts a tick every 25 ms. Worker timers keep running when the tab is in the background, unlike main-thread timers.
- **Lookahead.** Each tick schedules everything up to 120 ms ahead of `AudioContext.currentTime`, in slices of 1/8 beat.
- **`scheduleSlice()` is a pure function.** It takes the project, a target, a beat and an audio time, and returns where the next slice starts. The real-time engine, the offline renderer and the tests all implement its `ScheduleTarget` interface.
- **Loops.** The scheduler handles the cycle region: when it wraps, a new *segment* starts, audio clips resume part-way through and automation jumps to its value. Notes and audio are cut at the loop end so they never overlap the next pass.
- **Position.** The transport records `(audio time, beat)` markers at every slice and interpolates between them to find the playhead, which stays exact across loop wraps.
- **Count-in.** Playback starts one or two bars early, at a negative beat if needed. The metronome is forced on until the record point, and notes played during the count-in are ignored.
- **Automation.** Volume and pan breakpoints become linear ramps scheduled slice by slice.

## Instruments

Every engine implements `Instrument`: `noteOn(pitch, velocity, time)` returns a voice handle with `release(time)`, which the scheduler calls at the note's end. `BaseInstrument` keeps the voice set, steals the oldest voice above the polyphony limit and disconnects each voice's nodes when it finishes. Shared LFOs (vibrato, tremolo) are detached from a voice when it ends.

| Engine | Implementation |
| --- | --- |
| Subtractive | Per voice: 2 oscillators → resonant low-pass with envelope and key tracking → ADSR. A shared vibrato LFO modulates the oscillators' detune. |
| FM | Sine carrier and modulator with a decaying index, plus an optional fast-decaying high-ratio "tine" modulator. |
| Drums | Synthesised one-shots on General MIDI notes: pitch-swept sine kick, triangle + noise snare, burst clap, 6 inharmonic squares through band- and high-pass filters for hats (closed chokes open), toms, rim, crash. |
| Organ | Nine drawbars become one `PeriodicWave` per voice. The wave's fundamental is the 16′ sub-octave; each drawbar step is about 3 dB. Plus percussion (2nd/3rd harmonic), key click, vibrato, and a rotary stage (amplitude + pan swirl) whose speed changes with a smooth ramp. |
| Plucked strings | Pre-rendered (below). Extended Karplus–Strong: a filtered noise burst, comb-filtered for pick position, circulates in a fractional delay line through a blend of all-pass and averaging loss filters. The filter's delay is compensated so the string stays in tune, and the feedback gain gives the requested sustain time. Two peaking filters model the body. |
| Piano & mallets | Pre-rendered. Modal synthesis: a sum of exponentially decaying sinusoids, each generated by a damped two-pole resonator recurrence. The piano uses stiff-string partials `n·f·√(1+B·n²)`, a strike-position weighting, a detuned second string for beating, a longer aftersound and a hammer transient. Mallet models use measured-style mode ratios (e.g. marimba 1 : 3.99 : 10.65). |

### Pre-rendered instruments

Physical models are expensive to run voice by voice in the graph, but cheap to compute once. `RenderedInstrument` renders each note with the pure functions in `synth/render.ts` into an `AudioBuffer`. Buffers are cached per pitch and per velocity layer (4 layers) in an LRU cache of 96 notes, and played back with a release envelope. The cache is invalidated only when a parameter that changes the sound is edited; level and release don't count.

`prepare()` receives the notes a track will play and renders them in small batches on idle tasks, so playback never waits for synthesis. A first-time note takes about 1 ms (strings) to 10 ms (low piano notes).

The renderers are deterministic (seeded noise), and the tests check them for tuning using the tuner's pitch detector.

## Effects

Each insert is an `FxModule` (`input` → internal graph → `output`) that applies parameters incrementally. `FxChain` reconciles modules by slot id and rewires only when the order or bypass state changes. Parameter definitions (`fx/defs.ts`) drive both validation and the generated UI.

| Effect | Notes |
| --- | --- |
| Drive | AudioWorklet with 2× oversampling (interpolated midpoint) and a DC blocker; Soft, Hard, Tube (biased, asymmetric) and Fuzz curves. Falls back to a `WaveShaperNode` with the same curves. |
| Cabinet | Either biquad voicings (with level compensation for their resonant peaks) or convolution with a synthetic speaker impulse response (damped resonances + transient). |
| Reverb | Convolution with a procedurally generated stereo impulse response: exponentially decaying noise that darkens over time, plus early reflections. Regenerated (debounced) when the decay changes. |
| Delay | Feedback delay with a damping filter in the loop; free time or tempo-synced. |
| Chorus | Two short delays swept in opposite directions by one LFO, panned left and right. |
| Tremolo / Phaser | LFO-driven gain; four LFO-swept all-pass stages mixed with the dry signal. |
| Gain / EQ / Compressor | Native nodes with smoothing and make-up gain. |

Amp chains (`AMP_PRESETS`) are ordinary insert chains, level-matched so they peak at similar levels.

## Recording

- **Input.** The selected device is opened with voice processing disabled (no echo cancellation, noise suppression or auto gain). A channel splitter feeds a meter per channel and routes the chosen channel to a mono input bus, which is used for monitoring, the tuner and recording.
- **Audio capture.** A recorder AudioWorklet streams raw PCM in chunks of 2048 samples, each stamped with the audio-clock frame of its first sample. That gives:
  - **live drawing**: peaks are computed as chunks arrive and the take grows on the timeline;
  - **precise placement**: the first sample's beat is looked up on the transport's markers after subtracting the input and output latency reported by the browser;
  - **no decoding step**: the take is assembled directly into an `AudioBuffer`.
- **Count-in audio.** Audio recorded during the count-in is kept but hidden behind the clip's start `offset`.
- **MIDI.** A note is written into the take clip as soon as it is played and stretched while held. Non-loop takes grow bar by bar up to the playhead. In the cycle region, notes overdub into the loop-length clip.

## Tuner

The tuner reads 4096 samples of the input bus, halves the sample rate by averaging pairs, and runs **YIN** (cumulative mean normalised difference with parabolic interpolation). It analyses about 20 times a second and takes about 1.5 ms per analysis. A short median filter and per-note smoothing steady the needle.

## Persistence

- Projects are saved as one JSON document with the recorded audio embedded as base64 WAV.
- `validateProject()` treats any loaded file as untrusted: it drops unknown fields, fills defaults, clamps every value to its parameter range and regenerates missing ids.
- **Autosave** writes to `localStorage`. If the project is too large, the audio data is left out of the autosave.
- Machine-specific preferences are stored separately from the project: the input device and channel, the count-in length and the tuner settings.

## Desktop shell

- **Window.** Electron loads the same production build from disk, in a sandboxed window with context isolation and no Node integration. Only microphone and MIDI permissions are granted.
- **Smoke test.** `--smoke-test` loads the app hidden, checks that the UI rendered, that the audio engine booted and that the console stayed clean, prints a JSON report and exits 0 or 1. CI runs it on Windows, macOS and Linux before packaging.
- **Packaging.** electron-builder produces an NSIS installer and a portable `.exe`, a `.dmg` per architecture and an AppImage.
- **macOS signing.** Without a paid developer certificate, an `afterPack` hook applies an **ad-hoc signature**. arm64 Macs refuse to run a bundle whose signature was broken by packaging, and with the ad-hoc signature the user only sees the usual "unverified developer" prompt.

## Testing

Vitest covers the parts that are pure and therefore testable without a browser:

- project validation and round-trips (including every engine and effect type), clip splitting and naming, and preset ranges;
- the scheduler: timing, loop wraps, count-in, audio resumption, automation;
- the note renderers: tuning across the range, decay, bounded output;
- pitch detection, including harmonic-rich and noisy signals;
- WAV encoding, MIDI parsing and saturation curves.

Audio-graph behaviour is checked in the browser by rendering with `OfflineAudioContext` and measuring the output, and the desktop app by the smoke test.
